# 1 — Grids as graphs

## The vocabulary

A **graph** is two things:
- a set of **vertices** (also called nodes) — the "places"
- a set of **edges** — pairs of vertices that are directly connected

That's it. No pictures required, no computer science background. If
you know a social network's users (vertices) and which pairs are
friends (edges), you have a graph.

## The grid is a graph

The maze in this repo is a 2D array of characters — a grid. But if
you squint, it's a graph:

- Every open cell is a **vertex**
- Two open cells that are side-by-side (up/down/left/right) share an **edge**

Drawn out, a 3×3 open grid looks like this:

```
(0,0) ── (0,1) ── (0,2)
  │        │        │
(1,0) ── (1,1) ── (1,2)
  │        │        │
(2,0) ── (2,1) ── (2,2)
```

Nine vertices. Twelve edges. The walls in the maze just tell you
which of those edges don't exist.

**This is the reframe that unlocks everything.** Once you see the
grid as a graph, every graph algorithm applies to it — BFS, DFS,
Dijkstra, A\*, union-find. You don't have to learn a new algorithm
for grids; you apply the graph algorithm you already know.

## Why the reframe matters in interviews

Many LeetCode problems *look* like grid problems: "Number of
Islands," "Rotting Oranges," "Word Search," "Pacific Atlantic Water
Flow." A beginner approaches each one from scratch. Someone who
sees the graph underneath them writes nearly the same code every
time:

```python
def solve_grid_problem(grid):
    seen = set()
    for r, row in enumerate(grid):
        for c, _ in enumerate(row):
            if (r, c) not in seen and is_interesting(grid[r][c]):
                # BFS or DFS from here
                ...
```

The outer loop walks every vertex. The inner traversal does the
graph work. That's the template.

## Directed vs undirected

In our maze, if A is adjacent to B, then B is adjacent to A — the
edge goes both ways. That's an **undirected** graph.

If edges had a direction (A → B but not B → A), it would be a
**directed** graph. Web pages linking to each other, Twitter
followers, build dependencies, control flow in a program — all
directed.

The traversal code barely changes. In a directed graph you only
visit a neighbour if the edge points toward it.

## Weighted vs unweighted

Our maze's edges have no weight — "walking from one cell to the
next" costs the same everywhere. That's an **unweighted** graph.

If some edges cost more (think: mud, hills, toll roads), it's a
**weighted** graph, and BFS no longer finds the shortest path.
You need Dijkstra's algorithm instead — which is BFS with a
priority queue instead of a plain queue.

## What a graph is NOT

- **A tree** is a graph with exactly one path between any two
  vertices — no cycles. A maze generated by recursive backtracking
  is technically a tree (you can prove this: each cell is reached
  exactly once through exactly one wall). The extra passages this
  repo opens for variety turn it back into a general graph.
- **A grid is not the only kind of graph.** It's just the easiest
  one to draw. Real systems that are graphs: file systems,
  dependency trees, state machines, call graphs, infection
  networks, airline route maps, molecule structures.

## Try it

Open `../maze.py`. Look at the function `_neighbors(grid, r, c)` —
it yields the vertices adjacent to `(r, c)`. That function is the
only place the "grid-ness" matters. If you replaced it with a
function that yielded edges of a social network, the BFS and DFS
code would still work unchanged.

**That is the lesson.** The algorithm doesn't care what the
vertices represent.
